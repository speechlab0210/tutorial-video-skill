# Teaching design

## A teaching contract, not a table of contents

Start with a sentence of the form: “After this lesson, this audience can do X in situation Y and explain why.” For an introductory art-history talk, X might be distinguishing two interpretations using visible evidence; for an engineering workshop, debugging a particular failure. A talk can aim at understanding, judgment, or action without becoming an exam.

List the few prerequisites actually required. Choose one concrete running situation that the audience can understand without another lecture. Write an opening question whose answer will change as the lesson progresses. Identify the misconception the lesson must dislodge.

An effective progression often looks like:

**recognizable problem → attempted answer → observed limitation → necessary idea → worked example → changed situation → synthesis.**

This is an option, not a mandatory story formula. A historical account may need chronology; a proof needs logical dependencies; a safety procedure needs strict operational order.

## Concept order is part of correctness

Build a small dependency map: a learner must understand A before B can be meaningful. Use short, just-in-time prerequisite explanations. Avoid foreshadowing with unexplained specialist labels. “A harder case” is not a useful bridge if the audience does not yet know what makes it harder.

Keep section numbers, concept categories, process steps, and example numbers visually and verbally distinct. “The third capability” and “Part 3” can accidentally suggest the same taxonomy. Name the concept when there is ambiguity.

For each scene, ask:

- Which question does it answer?
- What must the learner already know?
- What changes in the learner's understanding?
- Why is the next scene necessary?

If a scene does not fit the opening promise, revise the promise, move the scene, or mark it optional, within the user's scope. Do not glue unrelated examples together with repeated “What about…” transitions.

## The transition-strip diagnostic

Extract the first and last teaching sentence from every scene into one list. Read that list without the rest of the script. This reveals oscillation, repeated restarts, unexplained terminology, unsupported conclusions, and section openings that describe only the first two pages.

Then map every scene to the section question. A map with no empty cells can still be wrong: read the actual content, because merely assigning an objective ID does not establish relevance.

For a targeted revision, inspect the preceding and following transition even if those scenes are outside the edit boundary. Report a cross-boundary issue instead of silently changing the neighboring chapter.

## Explain with an executable mental example

For an abstract mechanism, specify:

1. Actor and goal.
2. Information available at this moment.
3. Action or decision.
4. Observable result.
5. What this example establishes, and what it cannot establish.

Example: to teach weighted averages, show two fictional classes, their sizes, and their scores. Ask whether the classes or the individual learners receive equal weight. Compute each result, then change class sizes while holding their averages fixed. The change exposes the meaning of the denominator.

Use an analogy to make the entry easier, then explicitly map it to the real objects. State where it breaks. An analogy without the actual operation gives the learner a memorable story but no usable mechanism.

For a comparison, hold other factors constant when feasible. Same sentence with different emphasis, same data with different denominators, or the same task with and without a tool makes the changed variable visible. Label constructed examples as illustrations.

## Retrieval and transfer

Choose a task that reveals understanding: predict the next step, explain why a tempting answer fails, repair a flawed example, choose between two approaches, or transfer to a changed context. Provide feedback explaining the reasoning.

An expert audience may need one difficult counterexample rather than basic definitions. A public talk may use a rhetorical prediction and a short pause. A workshop should leave actual practice time. A recording should state when to pause and what to try.

If no real learner has tried the material, report an editorial comprehension review, not demonstrated learning gains.

## Time as a teaching constraint

First distinguish a flexible target from a hard slot. For a flexible target, clarify the ideas before optimizing length. For a hard slot, allocate time to essential outcomes, prerequisites, examples, practice, transitions, and the conclusion from the start.

When over budget, remove redundant examples, move detail to appendices, shorten setup, or narrow the learning goal. Preserve the explanatory step that makes the result intelligible. Estimate from a recorded sample, then replace estimates with measured times. Never label an estimate as actual runtime.
